# DM RMS 서버 운영 명령어 (FAB1/FAB2)

> 2026-11-10 GitHub `MinY96/DMRMS_Renewal`의 `run.py`, `requirements.txt`, `src/config/config.py`와 API 라우트 기준으로 작성했습니다. **Windows PowerShell 예시**이며, 실제 서버 IP·포트·계정·경로는 운영 `.env`를 우선합니다. 비밀번호는 소스나 문서에 기록하지 마세요.

## 1. 서비스 구분

| 폴더 | 실행 목적 | 실행 파일 | 비고 |
|---|---|---|---|
| `1_backup/fab1` | FTP 수집 → 파싱 → Matching 집계 | `run.py` | 배치 실행 (완료 후 종료) |
| `1_backup/fab2` | 현재 코드상 Matching 집계만 수행 | `run.py` | `collector.run()`과 `parser.run()`이 주석 처리된 상태 — **운영 의도인지 확인 필요** |
| `2_server/fab1` | FAB1 HTTP API 제공 | `run.py` 또는 Waitress | 계속 실행 |
| `2_server/fab2` | FAB2 HTTP API 제공 | `run.py` 또는 Waitress | 계속 실행 |
| `3_frontend` | Windows 설치 프로그램 | WPF 프로젝트 | FAB 선택 후 API로 데이터 통신 |

## 2. 최초 가상환경 설치 (사업장 서버별 독립 실행)

아래 예시는 FAB1의 API 서버 기준입니다. FAB2는 `fab1`을 `fab2`로 바꾸면 됩니다.

```powershell
cd D:\DMRMS_Renewal\2_server\fab1
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install --upgrade pip
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -c "import flask, pandas, psycopg2, oracledb, waitress; print('기본 의존성 확인')"
```

백업 서비스는 별도의 requirements 파일을 사용합니다.

```powershell
cd D:\DMRMS_Renewal\1_backup\fab1
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
```

## 3. 환경변수 확인

각 서비스 폴더의 `.env`는 서버마다 별도로 관리해야 합니다. 예를 들어 API 서버 `2_server/fab1/.env`에는 DB 연결 설정과 다음 항목을 확인합니다.

```dotenv
POSTGRES_SCHEMA=f1
DM_RMS_SERVER_HOST=0.0.0.0
DM_RMS_SERVER_PORT=5051
DM_RMS_DEBUG=false
```

FAB2의 서버는 `POSTGRES_SCHEMA=f2`로 변경합니다. 포트는 **FAB2가 다른 PC라면 같은 포트 사용이 가능**합니다. 같은 PC에서 두 서비스를 운영하면 포트를 다르게 설정하세요. 기존 PostgreSQL 계정·비밀번호, Oracle 접속값, 장비 FTP 설정은 기존 운영 설정을 그대로 사용해야 합니다.

## 4. API 서버 실행

**개발/연동 점검 용도** — Flask 내장 서버:

```powershell
cd D:\DMRMS_Renewal\2_server\fab1
.\.venv\Scripts\python.exe run.py
```

**실제 서비스 운영 권장** — Waitress:

```powershell
cd D:\DMRMS_Renewal\2_server\fab1
.\.venv\Scripts\waitress-serve.exe --listen=0.0.0.0:5051 --call src:create_app
```

FAB2에서는 FAB2의 폴더로 이동하여 동일하게 실행합니다. 실제 포트가 다른 경우 명령어의 `5051`을 해당 포트로 바꿉니다. 종료는 콘솔에서 `Ctrl+C`입니다.

> 프로젝트의 `2_server/fab*/run.py` 주석에는 `waitress-serve --call app:create_app` 예시가 있으나, 실제 Flask 앱 팩토리 모듈은 **`src`** 입니다. 위 명령의 `--call src:create_app`을 사용해야 현재 소스 구조에 맞습니다.

## 5. API 상태 및 기능 점검

다음 명령은 서버 **자체 PC에서** 실행합니다.

```powershell
# 헬스 체크: 서버/FAB/상태 확인
Invoke-RestMethod 'http://127.0.0.1:5051/api/health'

# Master Model 목록
Invoke-RestMethod 'http://127.0.0.1:5051/api/master/models'

# KLA2365 파싱 Parameter 목록 및 문자열 고유값
Invoke-RestMethod 'http://127.0.0.1:5051/api/master/parameters/options?model=KLA2365'

# KLA2365의 Master 기준정보 선택지
Invoke-RestMethod 'http://127.0.0.1:5051/api/master/filter-options?model=KLA2365'

# No Master Recipe 조회 가능 Model 목록
Invoke-RestMethod 'http://127.0.0.1:5051/api/no_master_detail/models'

# 특정 Model의 No Master Recipe 상세 조회
Invoke-RestMethod 'http://127.0.0.1:5051/api/no_master_detail/data?model=KLA2365'
```

`127.0.0.1`은 같은 PC에서 테스트할 때만 사용합니다. 클라이언트에서는 설정 파일 `3_frontend/DM_RMS.Wpf/api-hosts.json`에 입력된 FAB별 호스트를 사용합니다.

## 6. 백업 프로그램 수동 실행

```powershell
cd D:\DMRMS_Renewal\1_backup\fab1
.\.venv\Scripts\python.exe run.py
```

수집 주기 실행은 기존 **Windows 작업 스케줄러**나 사용 중인 운영 배치 체계를 유지합니다. 이 명령을 여러 번 동시 실행하지 않도록 작업 중복 실행 설정을 확인하세요.

**중요:** 2026-11-10 GitHub의 `1_backup/fab2/run.py`는 다음 줄이 주석 처리되어 있습니다.

```python
# collector.run()
# parser.run()
MatchingAggregator.run()
```

그러므로 현재 파일을 그대로 실행하면 FAB2에서는 FTP 수집과 파싱을 실행하지 않습니다. 별도의 배치가 존재하는지 운영 구성을 확인해야 하며, 이번 2차 패치에서는 백업 로직을 임의로 변경하지 않았습니다.

## 7. 운영 관리·안전 점검

- **로그**: 실행 콘솔의 오류와 각 서비스에서 사용하는 로깅 설정/파일 경로를 확인합니다.
- **프로세스 확인**: `Get-Process python,waitress-serve -ErrorAction SilentlyContinue` 또는 `Get-NetTCPConnection -LocalPort 5051`로 확인합니다.
- **백업**: 소스 교체 전 해당 서비스 폴더, `.env`, 현재 배포 버전 및 데이터베이스 백업을 확보하세요.
- **재기동**: 기존 API 프로세스를 정상 종료한 후 새 코드로 시작합니다. 중복 실행하면 포트 충돌이 발생합니다.
- **보안**: 개발 중인 API의 세부 Master/Recipe 수정 엔드포인트는 별도 서버 인증·권한 검증 여부를 반드시 확인해야 합니다. 단순한 WPF 버튼 비활성화는 접근 통제 수단이 아닙니다.
- **공개 저장소**: PostgreSQL 덤프와 `.dmrms_patch_backup_*` 디렉터리는 실제 사내정보를 포함할 수 있으므로 GitHub에 게시되지 않도록 별도로 관리합니다.
